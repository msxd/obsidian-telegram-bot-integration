# MSXD All-in-One Plugin — инструкции для агентов

Документ описывает конкретно этот проект. Правила здесь важнее общих привычек:
если что-то противоречит «как обычно делают в плагинах Obsidian» — следовать этому файлу.

## 1. Что это за плагин

Плагин Obsidian, который связывает **Telegram-бота** с хранилищем заметок (vault).
Две основные роли:

- **Входящие.** Бот принимает сообщения от пользователя и раскладывает их по заметкам
  в соответствии с настраиваемыми правилами.
- **Исходящие.** По команде в боте или по расписанию плагин отправляет пользователю
  определённые заметки.

Плагин персональный: один пользователь — один бот — один vault. Многопользовательских
сценариев, серверной части и внешних сервисов, кроме Bot API Telegram, не предполагается.

## 2. Текущее состояние

Реализовано:

- `src/settings.ts` — модель настроек, значения по умолчанию, `mergeSettings()`,
  `isChatAllowed()` и очистка мусора из `data.json`.
- `src/telegram/types.ts` — `ChatRef` и разбор объекта `chat` из Bot API.
- `src/telegram/api.ts` — общий вызов метода Bot API, `getMe`, `getRecentChats`,
  проверка формата токена, вычистка токена из текстов ошибок.
- `src/ui/token-section.ts` — поле токена (маскированное), кнопка показа, **Check token**, статус.
- `src/ui/allowed-chats-section.ts` — allowlist: список разрешённых чатов с удалением,
  кнопка **Refresh** и список недавно писавших чатов с кнопкой **Allow**.
- `src/inbox/*` — движок маршрутизации: разбор фильтров, подстановка переменных, выбор правила.
- `src/ui/inbox-section.ts` + `rule-modal.ts` — список правил с перестановкой и правилом
  по умолчанию в конце; редактор правила с живым превью пути на демо-сообщении.
- `src/telegram/updates.ts` — разбор апдейта Bot API в `IncomingMessage`.
- `src/inbox/writer.ts` — запись заметки: создание папок, создание и дозапись файла.
- `src/inbox/media.ts` + `vault-io.ts` — сохранение вложений и общие файловые операции.
- `src/intake/service.ts` — long polling, проверка allowlist, маршрутизация и запись.
- `src/ui/intake-section.ts` — переключатель приёма и статус.
- `src/ui/settings-tab.ts` — каркас вкладки, собирает секции; `src/ui/section.ts` — интерфейс
  секции и `replaceGroups()`.
- `src/main.ts` — только жизненный цикл: загрузка настроек и регистрация вкладки.

Ещё **не** реализовано (не описывать это как работающее и не полагаться на это в коде):

- альбомы не собираются в одну заметку: Telegram шлёт их отдельными сообщениями,
  каждое обрабатывается само по себе;
- файлы больше 20 МБ — Bot API не даёт их скачать, такое вложение пропускается
  с уведомлением, а текст сообщения всё равно сохраняется;
- правки сообщений: `edited_message` намеренно игнорируется, иначе правка легла бы в заметку
  вторым экземпляром;
- webhook — приём работает только через long polling;
- расписание и исходящие отправки;
- автотесты — инфраструктуры тестов в проекте пока нет.

Хвосты от шаблона sample-plugin: `README.md` всё ещё описывает пример, `versions.json`
содержит `"1.0.0": "1.0.0"`, хотя `minAppVersion` в манифесте — `1.11.0`.

## 3. Порядок работ

Итерации идут по одной, следующую начинать только по явному запросу — не забегать вперёд:

1. **Токен бота** — ввод, проверка, сохранение. *(сделано)*
2. **Привязка пользователя** — allowlist чатов, выбираемый из недавно писавших. *(сделано)*
3. **Приём сообщений** — long polling с сохранением `offset`. *(сделано)*
4. **Маршрутизация** — правила «сообщение → целевая заметка». *(сделано)*
5. **Исходящие** — команды бота и отправка по расписанию.

## 4. Структура и границы модулей

```
src/
  main.ts                     # только lifecycle: onload/onunload, регистрация вкладок и команд
  settings.ts                 # интерфейсы настроек, DEFAULT_SETTINGS, mergeSettings, isChatAllowed
  telegram/
    types.ts                  # доменные типы Telegram и их разбор из ответов API
    updates.ts                # разбор апдейта в IncomingMessage
    api.ts                    # HTTP-вызовы Bot API
  inbox/                      # движок маршрутизации: чистые функции, без UI и без Vault
    message.ts                # IncomingMessage — нормализованное сообщение
    filter.ts                 # разбор и применение фильтров правил
    template.ts               # подстановка переменных в шаблоны
    routing.ts                # выбор правила и вычисление пути заметки
    writer.ts                 # запись заметки в vault
    sample.ts                 # демо-сообщение для превью в настройках
  intake/
    service.ts                # цикл long polling и обработка сообщений
  ui/
    section.ts                # интерфейс SettingsSection и replaceGroups()
    settings-tab.ts           # каркас вкладки: только сборка секций
    token-section.ts          # секция токена
    allowed-chats-section.ts  # секция allowlist
    inbox-section.ts          # секция правил, включая правило по умолчанию
    intake-section.ts         # секция приёма: переключатель и статус
    rule-modal.ts             # редактор правила с превью
```

Правила:

- **Все сетевые вызовы живут в `src/telegram/`.** UI и доменный код обращаются к Telegram
  только через экспортируемые оттуда функции, а не через `requestUrl` напрямую.
- `src/telegram/` не знает ни про UI, ни про объект плагина: на вход — примитивы,
  на выход — типизированный результат или `TelegramApiError`.
- `main.ts` держать минимальным. Появилась логика — это новый модуль, а не ещё один метод плагина.
- Связь `ui → main` только через `import type` (иначе получится циклический рантайм-импорт).
- Файл разросся до ~200–300 строк — делить по ответственности.
- Вкладка настроек собирается из секций (`SettingsSection`): каждая секция владеет своей
  `SettingGroup` и своим временным состоянием. Новая группа настроек — новый файл-секция,
  а не ещё сотня строк в `settings-tab.ts`.
- Секция перерисовывает **свои** группы, а не вызывает `display()` вкладки: полная
  перерисовка сбрасывает фокус в полях ввода соседних секций.
- `SettingGroup` секции должны быть **прямыми детьми** контейнера вкладки. Obsidian
  расставляет вертикальные отступы между группами по их соседству, поэтому обёрточный
  `div` вокруг групп съедает верхний отступ у первой группы внутри него — визуально она
  прилипает к предыдущей секции. Если секции нужна перерисовка, она держит ссылки на свои
  корневые элементы и подменяет их на месте через `replaceGroups()` из `src/ui/section.ts`,
  а не заворачивает их в собственный контейнер.

## 5. Работа с Telegram

- **Только `requestUrl` из `obsidian`.** Не `fetch`, не `axios`, не node-модули: `requestUrl`
  обходит CORS и одинаково работает на десктопе и на мобильных.
- **Без сторонних Telegram-библиотек** (grammY, telegraf и подобные): они тянут Node API
  и вес в бандл. Работаем с HTTP Bot API напрямую.
- Запрос делать с `throw: false` и разбирать `response.text` вручную — иначе не прочитать
  тело ошибки Telegram (401, 404, 429 приходят с осмысленным `description`).
- **Токен не должен попадать ни в `Notice`, ни в консоль, ни в лог.** Он входит в URL запроса,
  поэтому текст любой пойманной ошибки пропускать через `redactToken()` перед показом.
- Ошибки Telegram превращать в `TelegramApiError` с сообщением, которое не стыдно показать
  пользователю: на английском, sentence case, с подсказкой что делать.
- Ответ Bot API не типизирован — проверять форму через type guard, а не приводить типы.
- 429: уважать `retry_after`, не устраивать повторы в цикле.
- **Очередь апдейтов расходуемая.** `getUpdates` с положительным `offset` подтверждает апдейты,
  и Telegram их удаляет — прочитать второй раз нельзя. Поэтому всё, что читает очередь
  «на посмотреть» (как `getRecentChats` для allowlist), обязано использовать **отрицательный**
  `offset`: он отдаёт хвост очереди, ничего не подтверждая. Положительный `offset` имеет право
  двигать только приём сообщений.
- Telegram хранит неподтверждённые апдейты **24 часа** — список недавних чатов в настройках
  по определению неполный, и в UI это сказано прямо.
- Одновременно читать очередь может только один клиент: параллельный `getUpdates` или
  установленный webhook дают **409 Conflict**. Пока приём включён, очередью владеет он:
  секция allowlist в этом случае берёт кандидатов из `IntakeService.getSeenChats()`,
  а собственный `getUpdates` делает только когда приём выключен.
- **`requestUrl` нельзя отменить** — у него нет `AbortSignal`. Поэтому висящий запрос
  long polling не прерывается при выгрузке плагина: `IntakeService` вместо отмены сверяет
  номер поколения (`generation`) и выбрасывает результат устаревшего запроса. Отсюда же
  следует, что сразу после перезапуска новый `getUpdates` может получить 409 от собственного
  недобитого запроса — это нормальная ситуация, лечится повтором с задержкой, а не ошибкой.

## 6. Настройки

- Настройки секционные: `settings.telegram.*`, дальше появятся `settings.inbox`, `settings.schedule`.
- `Object.assign` сливает объекты **поверхностно**, поэтому для вложенных секций он не годится:
  расширять `mergeSettings()` при добавлении каждой новой секции, иначе старый `data.json`
  не получит значения по умолчанию для новых полей.
- **Автосохранение по `onChange`** — идиома Obsidian. Отдельных кнопок «Save» не делать;
  кнопка появляется только под действие (например, проверку токена).
- Производные закешированные значения (`botUsername`) сбрасывать при изменении источника (токена),
  чтобы в UI не осталось данных от прошлого бота.
- **Allowlist работает fail closed:** пустой список разрешённых чатов означает «никому нельзя»,
  а не «всем можно». Это единственная преграда между vault и любым, кто найдёт бота,
  поэтому проверку `isChatAllowed()` нельзя обходить «пока настройки не заполнены».
- Список недавно писавших чатов — не настройка, а живое представление: держать его в памяти
  секции и обновлять по кнопке, в `data.json` не сохранять.
- **Текстовое поле сохраняет без перерисовки секции.** Перерисовка пересоздаёт `input`, и фокус
  слетает на каждом нажатии клавиши. Перерисовывать только то, что меняет состав списка
  (добавление, удаление, перестановка).
- `display()` перерисовывает вкладку целиком, поэтому точечные обновления (строка статуса)
  делать через сохранённую ссылку на элемент, а не повторным `display()` — иначе теряется фокус ввода.

## 7. Маршрутизация сообщений

Движок живёт в `src/inbox/` и не знает ни про Telegram API, ни про UI, ни про Vault: на вход
`IncomingMessage`, на выход путь заметки и заголовок. Благодаря этому его можно прогонять
скриптом вне Obsidian, чем и проверялась эта итерация.

- **Правила проверяются сверху вниз, первое совпавшее выигрывает.** Порядок в списке — это и есть
  приоритет.
- **Ни одно правило не совпало — сообщение берёт правило по умолчанию** (`inbox.fallback`).
  Оно всегда последнее в списке, его нельзя удалить, а фильтр у него фиксирован (`{{all}}`)
  независимо от того, что лежит в `data.json`, — иначе сообщению станет некуда деться.
  Правило с неразбираемым фильтром пропускается (в настройках оно помечено ошибкой),
  а не роняет всю маршрутизацию.
- **Формат записи задаётся правилом, а не глобально:** путь, медиапапка, заголовок, имя заметки
  и разделитель `---` — поля `MessageRule`. Пустые `mediaPath` и `noteName` берутся у правила
  по умолчанию, поэтому общая настройка для них не нужна.
- В `data.json` до этого фолбэк лежал россыпью полей (`folder`, `defaultHeading`, `mediaFolder`,
  `noteNameTemplate`, `separateMessages`), а разделитель был один на все правила.
  `sanitizeInbox()` переносит их в `fallback` и раздаёт `separate` каждому правилу —
  эту ветку миграции убирать нельзя.
- **Путь с расширением `.md` — это сама заметка** (несколько сообщений копятся в одном файле),
  всё остальное — папка, и имя внутри неё берётся из шаблона имени заметки.
- **Санитизируются только подставленные значения, не шаблон.** Иначе `/`, написанный в настройках,
  перестанет быть разделителем папок. Из значений вычищаются `\ / : * ? " < > | # ^ [ ]`,
  управляющие символы и переводы строк; пустые сегменты пути схлопываются, чтобы переменная,
  давшая пустоту, не оставляла дыру.
- **Для заголовка санитизация не применяется** — он попадает в текст заметки, а не в имя файла.
  Отсюда две функции: `renderPathTemplate()` и `renderTextTemplate()`.
- **Нераспознанная переменная остаётся в тексте как есть** — так опечатка видна в превью,
  а не превращается в молчаливо пустой сегмент.
- Форматы дат отдаются `moment` из `obsidian`, свой парсер форматов не писать.

Вложения (`src/inbox/media.ts`, `src/intake/service.ts`):

- Скачивание двухшаговое: `getFilePath()` меняет `file_id` на путь, `downloadFile()` забирает
  байты с `api.telegram.org/file/bot<token>/...`. Бот может скачать файл не больше **20 МБ**.
- **Папка вложений всегда папка**, не шаблон заметки: расширение диктует сам файл. Пустой
  `mediaPath` правила откатывается на общую медиапапку из настроек.
- `photo` приходит массивом размеров — берём **последний**, он самый большой.
- **Один файл может прийти сразу в двух полях**: анимация дублируется в `document` ради
  обратной совместимости, и без защиты гифка попадала в заметку дважды. Вложения
  дедуплицируются по `file_unique_id`, а порядок `ATTACHMENT_FIELDS` решает, какой вид
  выиграет — специфичный раньше `document`. Новое поле вложения добавлять с этим учётом.
- Имя берётся из `file_name` Telegram, а если его нет (фото, голосовые) — собирается как
  `<вид>-<messageId>.<расширение>`. Занятое имя получает числовой суффикс: **вложение
  не имеет права затереть существующий файл**.
- Ссылка строится через `fileManager.generateMarkdownLink()`, чтобы уважать настройки ссылок
  vault, и при необходимости дополняется `!` — медиа должно показываться внутри заметки.
- **Неудача со скачиванием не отменяет сообщение**: файл пропускается с `Notice`, текст
  сохраняется. Ошибку логировать только через `redactToken()` — путь скачивания содержит токен.

Реакция на принятое сообщение (`src/telegram/reactions.ts`):

- Telegram принимает **только свой фиксированный набор эмодзи**, поэтому в настройках стоит
  выпадающий список, а не поле ввода, и значение из `data.json` проверяется по списку.
- Эмодзи записаны escape-последовательностями и **без variation selector** (`\u2764`, не `❤️`):
  сравнение на стороне Telegram буквальное, лишний `U+FE0F` ломает совпадение. ZWJ-связки
  (`👨‍💻`, `🤷‍♂`) нужно сохранять целиком.
- **Неудача с реакцией — не неудача сохранения.** Бот может не иметь права реагировать, и тогда
  отказ повторяется на каждом сообщении, поэтому предупреждаем один раз за сессию приёма.

Запись в заметку (`src/inbox/writer.ts`, `src/intake/service.ts`):

- Порядок блока: заголовок, потом вложения, потом текст — как сообщение выглядит в Telegram.
- **Существующая заметка дозаписывается**, а не перезаписывается: путь вида
  `Journal/2026-09.md` копит сообщения за месяц. Дозапись идёт через `vault.process()`,
  чтобы параллельная запись не затёрла файл.
- **Разделитель `---` включается у каждого правила отдельно**, ставится только при дозаписи и только если в заметке уже что-то есть,
  и обязательно через пустую строку: `---` сразу под строкой текста Markdown понимает как
  подчёркивание заголовка (setext), а не как `<hr/>`.
- **Папки создаются по одному уровню** — `createFolder()` не обещает создавать родителей.
  Ошибку «уже существует» глотаем только если папка действительно появилась.
- **`offset` двигается даже если запись упала.** Иначе один неудачный путь заставит
  перезапрашивать тот же апдейт вечно и заблокирует всю очередь. Про неудачу сообщаем
  пользователю через `Notice`, но очередь идёт дальше.
- **Чужие сообщения отбрасываются молча** после `isChatAllowed()`, но чат всё равно
  запоминается в `getSeenChats()` — именно незнакомого отправителя и нужно предложить
  в кандидаты allowlist.

## 8. Секреты

- Токен хранится в `<Vault>/.obsidian/plugins/<id>/data.json` **открытым текстом**: Obsidian
  не предоставляет шифрованного хранилища. Это нужно честно писать в описании настройки и в README.
- `data.json` в `.gitignore` — не коммитить и не выводить его содержимое в ответах.
- Поле токена в UI — `type="password"` с явной кнопкой показа.
- Не логировать тела запросов и ответов Telegram без вычистки токена.

## 9. UI и тексты

- Строки интерфейса — **на английском, sentence case** («Bot token», «Check token»).
  Правило `ui/sentence-case` в ESLint это проверяет. Общение с пользователем в чате — на русском,
  но в код русский текст не попадает.
- Заголовки групп — через `SettingGroup.setHeading()` (доступно с Obsidian 1.11), не руками `<h2>`.
- Не делать в начале вкладки заголовок вида «General» или с названием плагина.
- **Никаких inline-стилей** (`el.style.*` запрещён правилом `no-static-styles-assignment`):
  классы в `styles.css` с префиксом `msxd-`, цвета — из переменных темы
  (`--text-muted`, `--text-error`, `--text-success`, `--size-2-2`).
- DOM собирать через `createDiv` / `createEl` / `createFragment`, не через `innerHTML`.
- Долгая операция — блокировать кнопку, показывать статус в UI и дублировать результат `Notice`.
- В редакторе правила (`.msxd-rule-modal`) строки **вертикальные**: подпись и описание сверху,
  поле на всю ширину снизу — иначе длинный шаблон пути не видно целиком. Контролы при этом
  прижаты вправо, чтобы кнопки и переключатель не разъезжались. На самой вкладке настроек
  раскладка обычная, в одну строку: поля там короткие.

## 10. Окружение и сборка

**Репозиторий лежит внутри рабочего vault:** `<Vault>/.obsidian/plugins/msxd-lifestyle-plugin`.
Сборка пишет `main.js` сразу туда, копировать артефакты никуда не нужно.

**Кросс-платформенная особенность:** `node_modules` ставились из-под Windows, а агенты работают
в WSL (linux). `tsc` и `eslint` работают в обеих средах, а `esbuild` — нативный бинарник:

- для сборки из WSL нужен `@esbuild/linux-x64`, для сборки из Windows/IntelliJ — `@esbuild/win32-x64`;
- сейчас в `node_modules` лежат **обе** платформы, ничего доустанавливать не требуется;
- если платформенный пакет всё-таки пропал, ставить его как
  `npm install --no-save --force @esbuild/<платформа>@<версия из package.json>` —
  `--no-save` не трогает `package.json` и `package-lock.json`, а обычный `npm install`
  удаляет пакет чужой платформы и ломает сборку на другой стороне.

Команды:

```bash
npm run dev     # esbuild в watch-режиме, main.js с inline sourcemap
npm run build   # tsc -noEmit + продакшен-сборка (минифицированная)
npm run lint    # eslint (включая правила eslint-plugin-obsidianmd)
```

Перед тем как считать задачу сделанной: `npm run lint && npm run build` — оба без ошибок.

Проверка в Obsidian: после сборки перезагрузить плагин (**Settings → Community plugins**,
выключить и включить) или выполнить команду **Reload app without saving**. Чтобы увидеть
изменения во вкладке настроек, её нужно закрыть и открыть заново.

## 11. Идентификаторы: несоответствие, которое надо решить

| Где | Значение |
| --- | --- |
| Папка плагина | `msxd-lifestyle-plugin` |
| `manifest.json` → `id` | `msxd-all-in-one-plugin` |
| `manifest.json` → `name` | `MSXD All-in-One Plugin` |
| `package.json` → `name` | `msxd-all-in-one-plugin` |
| Класс плагина | `MSXDAllInOnePlugin` |

Obsidian ожидает, что имя папки совпадает с `id`. Привести к одному значению нужно **до**
первого релиза: после публикации `id` менять нельзя. Агентам: самовольно не переименовывать,
спросить, какое имя считать основным.

## 12. Конвенции кода

- TypeScript strict; включён `noUncheckedIndexedAccess` — индексный доступ даёт `| undefined`.
- Форматирование по `.editorconfig`: табы, LF, UTF-8, одинарные кавычки, завершающий перевод строки.
- `isolatedModules` включён — импорты только типов помечать `import type`.
- Именование: классы плагина — `MSXD*`, типы настроек — `Msxd*` (исторически сложилось,
  без причины не переименовывать).
- `async`/`await` вместо цепочек промисов; ошибки не глотать молча — либо показать пользователю,
  либо пробросить.
- Всё, что требует очистки (события, интервалы, DOM-слушатели), регистрировать через
  `this.registerEvent` / `this.registerInterval` / `this.registerDomEvent`, чтобы выгрузка
  плагина не оставляла хвостов.
- Комментарии пишем по-английски и только там, где код не объясняет себя сам.

## 13. Do / Don't

**Do**

- Валидировать пользовательский ввод локально, прежде чем идти в сеть.
- Сообщения об ошибках делать конкретными: что пошло не так и что с этим делать.
- Оставлять плагин работоспособным при пустых настройках (нет токена — ничего не падает).
- Давать командам стабильные `id` и не переименовывать их после релиза.

**Don't**

- Не добавлять сетевые вызовы к чему-либо, кроме `api.telegram.org`.
- Не отправлять во внешний мир содержимое заметок, кроме того, что пользователь явно
  запросил через бота.
- Не выполнять удалённый код и не подтягивать скрипты в рантайме.
- Не трогать файлы за пределами vault.
- Не коммитить `main.js`, `data.json`, `node_modules`.

## 14. Политики Obsidian

Плагин должен соответствовать Developer Policies и Plugin Guidelines: работа по умолчанию
локальная, сетевые обращения — только ради заявленной функции и с описанием в README,
никакой скрытой телеметрии, аккуратная выгрузка без утечек слушателей.
